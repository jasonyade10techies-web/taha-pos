# Phase 5C staged implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement and verify each requested stage before the next. Preserve this plan and its continuation evidence across interruptions. This folder has no Git repository; record file-level backups and test logs instead of claiming commits.

**Goal:** Implement the owner's Phase 5C services, condition-aware inventory, customer timeline, receipt search, due-date/reminder and UI refinements without replacing the approved application.

**Architecture:** Extend existing repository interfaces and the custom PostgreSQL transaction functions with versioned migrations. Keep recognition deterministic and employee-safe; stock only changes inside completed sale/return/condition transactions. Use existing UI components and explicit local/demo counterparts; unsupported offline linked-material operations remain blocked.

**Tech stack:** Existing React/TypeScript/Zustand/TanStack Query, NestJS/PostgreSQL, IndexedDB demo and Tauri/SQLite boundaries.

**Spec:** `docs/PHASE5C_REQUIREMENTS.md` (owner-supplied requirements, copied verbatim).

## Global constraints

- Complete stages in order, testing each before proceeding; no Supabase integration or hosting deployment.
- Preserve Dashboard/POS/cart, Custom Service position, display, media/phone bridge, payments, permissions and receipts.
- Never expose costs/profit to unauthorized clients; unknown material acquisition cost stays unknown.
- All financial/stock writes are atomic, idempotent, store/actor-scoped and audited.
- No stock change during typing/cart add. Do not put a minimum field in Custom Service.
- Preserve browser/demo; block new stock-sensitive offline mutations until reconciled safely.
- Keep PKR, light-default approved branding, bundled fonts and white receipt/invoice paper.
- Use isolated financial test fixtures. No production reset, system installation or unsupported native success claim.

## Review focus

1. Legacy terminal identifiers and existing bridge UUID/pairings survive migration/reload; server accepts the actual frontend ID.
2. Similar models/variants/fuzzy matches never cause unconfirmed consumption or arbitrary location selection.
3. Return of a service-consumed material cannot restore twice or exceed sold material; unknown costs do not become fictitious profit.
4. Damaged transfers/recovery/write-off preserve physical totals and concurrency boundaries without entering sellable stock accidentally.
5. Ledger/reminders/search remain scoped, use current balances/real timestamps, and never imply WhatsApp delivery from opening a URL.
