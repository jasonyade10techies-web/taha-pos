# Windows local-data threat model

The server remains authoritative. The EXE contains only public configuration, not PostgreSQL credentials, signing secrets, privileged client keys or a backend administrator account. Access tokens stay in JavaScript memory. HttpOnly refresh cookies, offline grants and cached authentication context are encrypted using Windows DPAPI for the current OS user and stored outside localStorage. A revoked/unauthorized online refresh clears offline access. Offline authorization expires after eight hours; revocations cannot be learned while disconnected, so that is the bounded exposure window.

Native HTTP is restricted to the configured shop and owner-confirmed private LAN bridge origins. It refuses redirects and caller-supplied cookies. Production cloud requires HTTPS with ordinary certificate verification. LAN HTTP is separately permitted only for a trusted private endpoint, not as a cloud fallback. A compromised LAN or Windows user remains a threat; use trusted shop Wi-Fi, Windows account controls and BitLocker. Do not expose the LAN bridge publicly.

SQLite is not a secrets vault. It contains the minimum business data needed for the counter: cost-free catalogue, minimum retail prices, stock snapshot, counter customers, receipts, drafts and pending operations. Purchase costs and profit fields are rejected by the native cache, even for an owner. Customer and receipt data remains sensitive to anyone controlling the same Windows account; use disk encryption and limit Windows access. DPAPI does not protect against malware executing as that same user. Do not promise tamper-proof offline financial data from an unencrypted SQLite file.

An offline sale cannot authorize a server mutation by itself. The API verifies the signed terminal/profile/store grant, capture time, active session, current granular permissions, minimum/listed price, cash method, tax and stock. It executes the existing PostgreSQL transaction engine with locking, audit and idempotency. Conflicts roll back. Captured offline time/terminal are retained in append-only server import records. Pending grants are encrypted separately from SQLite. Logout clears session access but never deletes unsynced business operations.

Customer display is a separate native window with event-only permissions. It cannot call database, authentication, HTTP or owner configuration commands; those enforce the `main` window label. It receives a sanitized cart projection, excluding costs, minima, profit, stock locations/quantities, employee identity, approvals and internal notes. JavaScript has no generic native SQL or filesystem command.

Pending images live in private AppData, with size/format checks and explicit queue limits. Cloud storage is private through the existing permission-checked media API; S3 credentials are backend environment variables only. SQLite/AppData backup and encryption policies, update signing and installer signing must be finalized before production rollout.

The Windows WebView2 socket origin is explicitly http://tauri.localhost, alongside the native HTTP origin tauri://localhost. Release CSP allows the existing Socket.IO transport; its destination comes only from the owner-confirmed bridge configuration. Cloud HTTPS uses polling. These origin checks complement server authentication; they are not an authentication mechanism.
